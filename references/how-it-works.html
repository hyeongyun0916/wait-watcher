How waits-watcher works

A Claude session registers something you are waiting on. A loop on the same machine checks every open wait every 10 minutes, posts to Slack when one is done, and tells the session that registered it. The only store is the board artifact's database.

Flow

Which part runs which model

PartModelRuns whenDoes
Interactive sessionsthe session's modelwhen you or a session asksresolve the session, register, reset or close waits, answer "what am I waiting on?", run waits.sh check <id> right after registering
Check run (claude -p)Sonnet (MODEL)once every 10 min, 15 min capcheck each open wait read-only, write results, purge archived waits after 24 h, write the Slack text, and tell the waiting session "the wait is over, go check"
waits.sh loopno modelalways, while the machine is upstart the check run, parse its results, post Slack texts via webhook, warn after 18 failed runs in a row
Board pageno modelwhen openedshow the database live; memos, cancel, reset, archive, add to-dos

Almost all cost is the check run, and it grows with the number of open waits.

What keeps running

waits.sh loopA setsid process; its pid is in ~/waits/loop.pid. It dies when the machine or container restarts; start it again with waits.sh start.
claude -p (Sonnet)Started by the loop every 10 minutes and gone when done. Runs in permission mode auto (sessions hold messages from a bypassPermissions sender) with a deny list that blocks Slack posting, gh writes, git, kubectl and curl.

The database (the only copy)

waits/<id>Waits are w…, to-dos t…. Status open · done · stuck · cancelled; archived ones carry deleted_at.
meta/statusLast run time and "open N · done M · errors K".
meta/sessionsSession list for the board's to-do picker, kept in sync with live sessions by the check run.
